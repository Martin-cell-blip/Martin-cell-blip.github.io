佐证页 · 素材调取台

他们解决了搬运，没解决定位

影视飓风公开过一套完整的素材搬运方案：1000TB SSD 加 320 盘磁带、24 芯光缆串起所有办公楼、剪辑师点播放时系统自动把素材从磁带预转到 SSD。公开资料里没有任何东西回答上一个问题：剪辑师怎么先知道要找的是哪一条。

这一页只做两件事：把素材元数据模型定出来，把冷热分层下的检索与回迁做出来。 这是主打作品之外的一块证据，不求做成完整产品。它要证明的是：我看得懂剪辑师找素材时会用的查询条件。

回迁计划

冷热分层下的批次合并

磁带的成本不在读取速度，在装载次数。换一盘带的机械开销远大于多读几条。所以剪辑师一次勾选 6 条冷层素材时，正确做法是按磁带号合并成批次，同一盘带上的素材一次取完，而不是发 6 个独立请求。

元数据模型

每个字段都标注来源

字段分三档：官网实测直接抄自他们对外素材库的卡片；JD/公开来自招聘 JD 或公开视频里明确出现的概念；推断是我按冷热分层的需要补的，没有证据说他们已经有。

字段类型来源为什么需要它
clip_idstring PK推断主键。素材可以改名、可以转码，但引用它的地方不能断。
projectstring官网实测官网卡片就是「样片日记-南非」这种项目/合集归属。
shot_sizeenum(5)官网实测全景/远景/中景/近景/特写。剪辑师找镜头的第一维度。
topicstring[]官网实测可二级，官网出现过「动物-长颈鹿」这种写法。
camera_brandenum(12)官网实测DJI/SONY/RED/BMD… 决定素材能不能和同场次其他机位配。
resolutionstring官网实测4K/6K/8K。
fpsdecimal官网实测59.94 与 60 不是一回事，混用会掉帧。
color_spaceenum官网实测S-Log3/D-Log/N-Log/Log3G10。决定能不能直接进时间线的字段。
tc_in / tc_outtimecodeJD/公开DIT 岗 JD 明写"素材全生命周期管理"。
checksumstringJD/公开他们自研的 Gate 拷卡软件就做 MD5/XXHASH64 校验。
storage_tierenum(3)JD/公开SSD 热层 / 磁带冷层 / 仅代理。1000TB SSD + 320 盘磁带是公开数字。
tape_idstring推断回迁批次合并的依据。没有它，冷层就只能逐条取。
proxy_statusenum(3)推断有代理才能在不回迁的情况下先看。
recall_stateenum(4)推断未回迁/排队中/回迁中/已在热层。
archived_atdatetime推断降冷时间，用于回看降冷策略是否合理。
last_used_atdatetime推断旧素材复用的前提是知道它上次被谁用过。
为什么不自己发明一套字段。他们的对外素材库已经在用「景别 / 内容 / 机型 / 帧率 / 色彩空间」标注每一条素材。 这说明公司内部已有跨机型跨项目的标注习惯，而且这套词汇正是剪辑师开口要素材时会说的话 （"给我找个西藏那次的航拍全景，最好是 RED 拍的"）。产品经理在这里要做的是把已经存在的口头词汇变成可检索的字段，而不是设计一套分类法。

这一页证明不了什么

  1. 素材是我自己的摄影素材，12 条。他们是 4000TB、2025 年一年拷了约 1PB。规模差了六个数量级，检索在小库上好用不代表在大库上好用。
  2. 磁带号是我编的。公开资料只说了"320 颗 12TB 磁带"，没有任何关于编号规则、单带容量利用率、素材如何分配到带的信息。批次合并的收益依赖这个分布，换一种分配方式收益会完全不同。
  3. 装载次数不等于时间。没有 LTO 库可测，所以只报次数不报秒数。
  4. 没做语义检索。这一页只做 facet 过滤和关键词匹配。做向量检索会让这一页变成一个技术演示，而这一页要证明的是我懂剪辑师的查询语言，不是我会调向量库。
  5. 他们可能已经有了。2026 年新招的 Java／SRE／全栈很可能正在做这件事。我的判断依据是"公开资料里我没找到"，不是"他们没有"。
